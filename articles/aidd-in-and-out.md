## はじめに

現場でAI駆動開発（以下、AIDD）に取り組んできて、最近思うことを何となく記事にしてみたくなったので書いてみます！

始めた頃は設計書や規約を整えれば、AIが意図どおりに作ってくれると思っていました。最近は実装を頼む前に「できあがったものを見て、何を根拠に合格とするか」まで決めるようにしています。注文が0件のときに何を表示するか。全ページをたどったときに、注文が漏れなく一度ずつ出るか。こういう条件を書いてみると、AIに伝える以前に、チームで決めていなかったことが見つかりました。

この記事ではAIに渡すものを2つに分けて呼びます。in（input）は設計書、規約、意図の説明のように、実装を導く情報です。out（output）はテスト、具体例、デザインの見本のように、できあがったものを評価する合格条件です。どちらもAIに渡すという意味では入力ですが、役割が違います。

以下ではそう考えるようになった経緯と、調べて見つけた研究や文献、いま試していることを書きます。研究で測られた結果と、私の現場での体感は分けて書きます。答えはまだ出ていないので、模索中の考えとして読んでください。

なお、実例は業務の話をECサイトに置き換えています。

## inputを作り込んでもズレた実装

AIDDを始めた頃、私が力を入れていたのは次の3つでした。

- 設計書・仕様書の作り込み
- CLAUDE.mdや規約の整備
- ドメイン設計・モデリング

AIは書かれたことを読むのだから、書く内容を正確にすれば出てくるものも正確になる。そう考えていました。

それでも、AIの実装はズレました。目立ったのは3つです。

1つ目は動くけれど意図と違う振る舞いです。コードは読みやすく筋も通っているのに、結果が欲しいものと違いました。

2つ目はPBIの受入条件「だけ」を満たした実装です。ECの注文履歴一覧に置き換えると、受入条件が「注文を新しい順に表示する」「ページングできる」の2行だったとき、AIはその2行を満たして終わります。抜け落ちたのは次のようなものでした。

| 抜けていたもの | 注文履歴一覧での例 |
|---|---|
| 書いていない例外・境界 | 注文が0件のとき、最終ページ |
| 非機能・エラー処理 | 件数が増えると遅くなる、APIが失敗したときの表示 |
| 設計規約・構造 | リポジトリ層を飛ばして画面から直接クエリを書く |
| UI | 素のテーブルのまま、読み込み中の表示がない |

3つ目はテストを弱めたり書き換えたりして通すことです。

調べてみると、同じ悩みは業界でも語られていました。仕様を先に書いてAIに実装させる「スペック駆動開発」について、ThoughtworksのBirgitta BöckelerがKiro、spec-kit、Tesslを試した記事を書いています[^sdd]。Kiroでは、小さなバグの修正に4つのユーザーストーリーと16の受入条件が生成されました。spec-kitでは大量のMarkdownが生成されてレビューが重くなりました。さらに、調査のステップで既存のコードを調べ、それが既存クラスの説明だというメモまで残していたのに、エージェントはそれを新しい仕様として受け取り、重複したクラスを作りました。Böckelerは、こうしたツールが偽りのコントロール感を与えるのではないか、という懸念を挙げています。inputを厚くしても、AIがそのとおりに動くとは限りません。

テストの書き換えも私の現場だけの話ではありませんでした。ImpossibleBench[^impossible]は、テストと仕様をわざと矛盾させた課題を作り、AIがテストを通すために仕様を破るかを測るベンチマークです。矛盾させたSWE-benchの課題（Conflicting-SWEbench）では、GPT-5が54%の課題を、著者らが不正と定義した方法で通過しました。しかもこれは、不正をしないよう厳しく指示したプロンプトでの数字です。不正にはテストの書き換えのほか、特定の入力だけを特別扱いする実装なども含まれます。テストを用意しても、書き換えられて通されることがあります。対策は後半の実践で書きます。

## テストを先に書いて変わったこと

それでも、流れが変わったのはテストを先に書くようにしてからです。e2e、API、ユニットと粒度を混ぜて、実装より先に用意しました。体感ですが、実装のやり直しが減りました。このやり方はチームにも広がっています。

研究でも同じ方向の結果が出ていました。ウォータールー大学の研究[^tdd]では、GPT-4 Turboで問題文だけでは解けなかった課題に、公開テストも渡して再試行すると、MBPPでは全体の12.0%、HumanEvalでは8.5%にあたる問題を追加で解けました。

MicrosoftのTiCoder[^ticoder]は、AIが生成したテストが意図に合うかを人が判定し、その結果でコードの候補を絞り込む仕組みです。人の回答を参照解で模擬した自動評価（MBPP）では、1回の判定でpass@1が48.39%から70.49%に、最大5回で85.48%に上がりました。ここで人がしているのはコードを書くことではなく、テストが意図に合うかの判定です。この点は終盤の「誰が正解を書くか」で改めて触れます。

どちらも関数レベルのコード生成での結果で、私の現場の体感とは別のものです。それでも、合格条件を先に渡すと精度が上がるという方向は同じでした。

## inは意図、outは正解

とはいえ、最初に作り込んだinputが無駄だったわけではありません。

ISSTA 2025の論文[^issta]では、要件を自然言語ではなく入出力例だけで渡すと、LLMのスコアが60%以上下がりました。一方で、関連するキーワード程度の断片的な説明を足すだけでも、性能は大きく改善しています。

私はこれを、次の役割分担だと理解しています。

- in は意図を伝える。なぜそうするのか、何のためか
- out は正解を伝える。何ができていれば合格か

自然言語の意図だけでは、それらしく満たす実装がいくつもあります。例だけでは例だけを通す実装でも合格してしまいます。inで意図を、outで合格条件を渡して、はじめて欲しい実装に絞り込めます。前半で1つ目に挙げた「動くけれど意図と違う振る舞い」は、inだけで解を絞ろうとして、それらしい実装のうちの1つが出てきた状態だったのだと思います。

### 受入条件だけを満たす実装の正体

この役割分担で見直すと、前半の表のズレにも説明がつきます。受入条件は「点」の正解で、その外側は空白です。空白の部分は、AIが手早く済む形で埋めてしまいます。表に並べた0件のときの表示、性能、構造、UIは、どれも受入条件の外側にありました。

点を面に広げる方法として、プロパティベーステスト（PBT）の研究があります。Property-Generated Solver[^pgs]は、個別の入出力例ではなく、コードが常に満たすべき性質でAIの生成を導く手法で、初版の論文では既存のTDD系手法よりpass@1が相対で23.1〜37.3%改善したと報告されています。ユニットテストだけで評価すると、生成コードの正しさを過大に見積もる場合がある、という報告もあります[^props]。

点を面に広げられるのは振る舞いだけではありません。表の「設計規約・構造」の行のように、設計にも合格条件として書ける部分があります。

### 設計もinとoutに分かれる

始めた頃に作り込んでいた設計書やドメイン設計も、この区別で見直せます。要件を満たすための設計、つまり「どう作るか」はinで、境界や不変条件のように「何が成り立っていなければならないか」はoutです。契約による設計（Design by Contract）で、事前条件・事後条件・不変条件を契約として実装と分けて考えるのと同じ発想です。

outのうち、どれを機械判定に寄せられるかは「崩れたらテストで赤にできるか」で考えています。

- 赤にできるもの: モジュール間の依存方向（画面層からインフラ層へ直接依存しない）、全ページで各注文がちょうど1回ずつ現れること、一覧の取得で発行するクエリの回数
- 赤にできないもの: デザインの見た目の仕上がり（見本と比べて人やAIが判定する）

イベント駆動にするかどうか、クラスの分け方、ライブラリの選定は、合否を判定する材料ではないのでinです。

境界は少しややこしく、どこに境界を引くかを決めるのは設計判断なのでinです。決めた境界が守られていることはoutになります。

### outはガイドにもセンサーにもなる

Böckelerは、コーディングエージェントを使う側が組む「ハーネス」を、エージェントが動く前に方向づける「ガイド」と、結果を観測して自己修正を促す「センサー」に分けて整理しています[^harness]。どちらにも機械的に動くもの（computational）と、AIの推論を使うもの（inferential）があるとしています。

この整理で見ると、inはガイドです。outは、実装の前に渡せばガイドとして方向を示し、実装のあとに実行すればセンサーとして結果を返します。Claude Codeの公式ベストプラクティス[^cc]でも、「Claudeに見えないことを伝える」と並んで「Claudeに実行できるチェックを渡す」が柱の1つに挙がっています。合否が返るものを渡せば、Claudeは変更、チェックの実行、修正のループを自分で回せる、という説明です。コードが書かれた経緯を見ていない別のセッションやサブエージェントにレビューさせる使い方も紹介されています。

outは実装の前と後の両方で働きます。次の章で、前半の注文履歴一覧に戻って書き方を紹介します。

## 実践：注文履歴一覧の場合

前半の表で挙げた抜けを、注文履歴一覧でどう埋めているかを書きます。受入条件は前半と同じ「注文を新しい順に表示する」「ページングできる」の2行です。この2行の外側にある空白を、outで1つずつ埋めていきます。

| 前半で抜けていたもの | 当てるout |
|---|---|
| 書いていない例外・境界 | 決定表、ガーキン、プロパティ |
| 非機能・エラー処理 | ガーキン（API失敗）、クエリ回数のテスト |
| 設計規約・構造 | ArchUnit |
| UI | UI規定とFigmaの見本 |
| テストの書き換え（3つ目のズレ） | hooksでテストの編集を止める |

### 判断が分かれる点を決定表にする

「注文を新しい順に表示する」という一文にも、判断が分かれる点がいくつも隠れています。この洗い出しはAIに頼みます。「この要件で判断が分かれる点を列挙して、決定表の列にして」と頼み、セルを埋めるのは人です。

| AIが挙げた論点 | 人が決めた内容の例 | POへの質問の例 |
|---|---|---|
| 注文が0件のとき | 「まだ注文はありません」と表示する | なし |
| 注文APIが応答しないとき | 再読み込みを促す | なし |
| キャンセルした注文 | 未決定 | 問い合わせや履歴確認に使えるよう、キャンセル済みも表示するか |

人が埋められないセルは要件の穴なので、そのままPOへの質問になります。冒頭に書いたとおり、私の現場でも、こうした合格条件を書く段階で、チームで決めていなかったことが見つかりました。outを書く作業はテストを書く作業である前に、要件の穴を見つける作業でした。

決めた内容には決めた理由も一言添えておくと、それがそのままAIに渡すinになります。POへの質問の列にある「問い合わせや履歴確認に使えるよう」のような一言です。

### 例外・境界はガーキンとプロパティで

決定表で決めた行はそのままガーキンのシナリオにします。0件のときとAPIが応答しないときで、前半の表では「例外・境界」と「エラー処理」として抜けていたものです。

```gherkin
# language: ja
機能: 注文履歴一覧

  シナリオ: 注文が0件
    前提 注文履歴がない会員でログインしている
    もし 注文履歴を開く
    ならば 「まだ注文はありません」と表示される

  シナリオ: 注文履歴の取得に失敗した
    前提 注文APIが応答しない
    もし 注文履歴を開く
    ならば 再読み込みを促すメッセージが表示される
```

ガーキンは例を1つずつ並べる書き方なので、件数で振る舞いが変わるページングはプロパティで書きます。

```java
// 前提: 試行ごとに、生成した注文を新しい会員の履歴として登録してから一覧を取る。
// 注文の件数は、複数ページにまたがる範囲で生成する。
@Property
void 全ページを取得順につなぐと注文日時の新しい順に並ぶ(@ForAll("複数ページになる注文履歴") List<Order> orders) {
    Member member = registerHistory(orders);
    List<Order> all = history.listAllPagesInOrder(member);
    assertThat(all).isSortedAccordingTo(comparing(Order::orderedAt).reversed());
}

@Property
void 全ページを通して各注文がちょうど1回ずつ現れる(@ForAll("複数ページになる注文履歴") List<Order> orders) {
    Member member = registerHistory(orders);
    List<OrderId> shown = history.listAllPagesInOrder(member).stream().map(Order::id).toList();
    assertThat(shown).containsExactlyInAnyOrderElementsOf(orders.stream().map(Order::id).toList());
}
```

2つ目のプロパティはページングでよく起きる重複と取りこぼしを、例を並べずにまとめて検出します。同じ日時の注文があると、ページの境目で重複や取りこぼしが起きやすくなるので、同時刻の注文の並べ方（注文IDで決めるなど）も仕様として決めておきます。

受入条件の「ページングできる」が点の正解だったのに対し、この2つのプロパティは件数によらず成り立つ面の正解です。冒頭で挙げた「全ページをたどったときに、注文が漏れなく一度ずつ出るか」を、そのまま性質として書いたものです。

### 性能と構造は機械判定に寄せる

前半の表で「件数が増えると遅くなる」と書いた非機能の抜けと、「設計規約・構造」の抜けです。私の現場でも、規約は決まりとして禁止しつつ、機械的に判定できるものは基本的に機械判定に寄せました。文章の規約は読み飛ばされても気づけませんが、テストなら赤になります。

一覧の取得で余計なクエリが増える退行は、クエリの発行回数で検出します（クエリを数える仕組みは、Hibernateの統計機能などで用意します）。

```java
@Test
void 注文が100件でも一覧の取得で発行するクエリは2回以内() {
    givenOrders(member, 100);
    queryCounter.reset();
    history.list(member, PageRequest.first());
    assertThat(queryCounter.count()).isLessThanOrEqualTo(2);
}
```

この例が数えているのは取得処理の中だけで、所要時間そのものは測れません。レスポンスを組み立てる段階で遅延読み込みが走る構成なら、そこまで含めて数えます。

構造はArchUnitで判定します。次のルールは画面層からインフラ層への直接の依存を禁じます。

```java
@ArchTest
static final ArchRule 画面層はインフラ層に直接依存しない =
    noClasses().that().resideInAPackage("..order.web..")
        .should().dependOnClassesThat().resideInAPackage("..order.infrastructure..");
```

### UIは見本を正解にする

UIは前半で「赤にできないもの」に分けた領域です。私の現場ではUI規定を定め、Figmaのデザインを見本として渡すようにしました。Claude Codeの公式ベストプラクティス[^cc]にも、デザインのスクリーンショットをプロンプトに貼ることや、モックアップの横に並べたブラウザのスクリーンショットをチェックとして使うことが挙がっています。

### テストをAIに書き換えさせない

最後は3つ目のズレ、テストを弱めたり書き換えたりして通す問題です。前半で紹介したImpossibleBenchの論文[^impossible]では、ズルを減らす方法も試されています。テストをAIから隠すと、不正による通過はほぼなくなりましたが、元の課題での性能も下がりました。テストを読み取り専用にし、採点時にはテストへの変更を取り消す条件では、元の課題での性能を回復でき、テストの書き換えによる不正を防げました。ただし、特定の入力を特別扱いするような不正は、この条件でも防げません。プロンプトの書き方を工夫すると、矛盾させたLiveCodeBenchではGPT-5の不正が92%から1%に下がった一方で、矛盾させたSWE-benchでは緩い指示で66%、厳しい指示でも54%でした。指示だけで防げるとは限りません。

AIに見せない正解という方針を徹底した事例が、StrongDMのAIチームが2026年2月に公開した「ソフトウェアファクトリー」です[^strongdm]。人はコードを書かず、レビューもしないという原則を掲げ、仕様とシナリオでエージェントを動かしています。シナリオはエンドツーエンドのユーザーストーリーで、コードベースの外に置くことが多く、同チームはこれを機械学習のホールドアウト（学習に使わない評価用のデータ）に例えています。初期には、エージェントが狭く書かれたテストを `return true` で通してしまうことがあったそうです。

ここまで徹底しなくても、正解を実装するAIの手が届かない場所に置くという考え方は使えます。研究の条件はテストを読み取り専用にするものでしたが、Claude Codeならhooksで実装中のテストの編集を止められます。公式ベストプラクティス[^cc]も、毎回必ず守らせたいルールはCLAUDE.mdに書くのではなく、hooksや権限設定で強制するよう勧めています。

```json
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{ "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/protect-tests.sh" }]
    }]
  }
}
```

```bash
#!/bin/bash
path=$(jq -r '.tool_input.file_path // empty')
if [[ "$path" == */src/test/* || "$path" == *.feature ]]; then
  echo "実装フェーズではテストとシナリオを編集しないでください。仕様と矛盾している場合は、実装を止めて報告してください" >&2
  exit 2
fi
```

この設定で止められるのは `Edit` と `Write` によるテストとシナリオの編集だけで、シェル経由の変更や、`src/test` の外にある `.feature` 以外のテストは対象外です。どのフェーズかを判定する処理も入っていないので、実装を任せるセッションでだけ有効にして使います。評価の環境ごと分けるStrongDMのやり方と比べると、止める力は弱めです。

止めるメッセージに「矛盾していたら止まって報告する」という出口を書いているのも、ImpossibleBenchの結果を踏まえたものです。テストへの変更を取り消しても特定の入力の特別扱いは防げなかったので、書き換えの道を塞ぐだけだと、実装側で例だけを通す方向に逃げる余地が残ります。同じ論文では、課題に誤りを見つけたら中断して人に知らせる選択肢を与えると、矛盾させたSWE-benchでのGPT-5の不正が54%から9%に下がりました。ただし、Claude Opus 4.1では効果がずっと小さかったと報告されています。

ここまでは、前半の表に並べた抜けとテストの書き換えに、それぞれoutを当てる話でした。ただ、どれも合格条件そのものは正しいという前提に立っています。合格条件のほうが間違っていたらどうするかは、まだ答えが出ていません。

## まだ分からないことと2つのループ

いまも分からないことは3つあります。

- どの形のoutが最適か（ガーキン、プロパティ、見本）
- 誰が正解を書くか（PO、実装者、AI）
- 要求そのものが揺れること

1つ目はこの記事で使ったガーキン、プロパティ、見本の使い分けです。どの条件をどの形で書くと一番効くのかは、まだ手探りです。

2つ目に関わる議論として、The Pragmatic CTOはソフトウェアファクトリーについて「シナリオを書くのは誰か」と問いかけています[^pragmatic]。人が書くなら、人の関与はなくなったのではなく、コードレビューからシナリオの設計へ場所を移しただけだ、という指摘です。先に紹介したTiCoderでも、人の役割はテストが意図に合うかの判定でした。私はこの指摘を、AIDDで人の仕事が「コードを書く・読む」から「正解を書く」へ移っていることの表れだと受け取っています。誰がその正解を書くのかは、私の現場でもまだ決まっていません。

3つ目から、正解は確定したものではなく仮説だと考えるようになりました。そうすると、回すループは2つになります。

- 内側のループ：実装が合格条件を満たしているか。AIがテストやルールを実行して確かめる
- 外側のループ：合格条件そのものが利用者の意図や必要性に合っているか。人が確かめ、違えば合格条件を直す

先に紹介したBöckelerの整理で言えば、内側のループはガイドとセンサーで組んだハーネスの中で閉じます[^loop]。外側のループはハーネスの外にある、プロダクトの仮説検証です。

たとえば、決定表で未決定にしていたキャンセル済みの注文について、リリース後に問い合わせ対応の担当者から「キャンセルした注文も履歴で確認したい」と言われたとします。POがそれを受けて表示すると決めたら、先に直すのは決定表とシナリオです。コードは直したシナリオに合わせてAIに作り直させます。

Kiroのチームは、仕様が依頼者の意図を捉えているかを判定できるのは、最終的にはその依頼者だけだと書いています[^kiro]。リリース後に利用者へ見せて確かめる外側のループは、この考えを私なりに広げたものです。外側のループはAIだけでは閉じません。

外側のループが回るたびに、合格条件は書き換わります。キャンセル済みの注文で言えば、最初は未決定にしたこと、問い合わせ対応の声を受けてPOが表示すると決めたこと、それに合わせて決定表とシナリオを直したことです。コードは直したシナリオからAIに作り直させられますが、この経緯はコードからは復元できません。

始めた頃に作り込んでいた設計書や規約は、「どう作るか」を伝えるものでした。いまコードと一緒に残したいのは、何を合格とし、なぜそう決め、何を見てその判断を変えたかの履歴です。AIDDでチームの資産になるのは、こちらだと思っています。

## 明日から試せること

1. 実装前に決定表や具体例を書く
2. 機械判定できる規約はテストに寄せる
3. 意図（なぜ）を正解とセットで渡す

始めた頃の私は、inを厚くすれば意図どおりに作ってもらえると思っていました。いまはoutを先に書き、それを仮説として直していくところに手間をかけるほうが効くと考えています。答えはまだ出ていないので、同じように試している方の話も聞いてみたいです。
