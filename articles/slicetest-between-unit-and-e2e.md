「ユニットテストはもう要らない、E2Eテストに寄せればいい」という意見を最近よく見かけます。

言いたいことは分かります。DBや外部APIをモックしたユニットテストは、SQLの間違いやマイグレーション漏れ、外部APIに送るリクエストの形の間違いを素通りさせます。本番で壊れるのは、だいたいモックで隠していたところです。

ただ、E2Eに寄せると今度は別の問題が出ます。ブラウザを動かしてデプロイ済みの環境に対して流すので遅いし、不安定になりやすいし、落ちたときにどこが壊れたのか分かりにくい。外部APIが500を返したときの挙動を確かめたくても、E2Eで再現するのは大変です。

欲しいのは、その間にあるテストだと考えました。アプリは本物のプロセスとして動かし、DBも本物を使う。ただしブラウザは使わずHTTPで直接叩き、自分たちの管理外である外部APIだけを差し替える。

それを書くためのフレームワークとして slicetest を作りました。

- GitHub: https://github.com/revo1290/slicetest
- npm: https://www.npmjs.com/package/slicetest

## ユニット・E2Eとの違い

| | ユニットテスト | slicetest | E2Eテスト |
|---|---|---|---|
| アプリ | 関数・クラス単位 | 本物のプロセス | デプロイされた環境 |
| DB | モック | 本物の Postgres | 本物 |
| 外部API | モック | スタブサーバー | 本物かサンドボックス |
| ブラウザ | なし | なし（HTTPで叩く） | あり |

アプリを切り出して（slice）テストするので、この名前にしています。

## どんなテストになるか

「投票を作ると、DBに保存されて、Slackに通知される」という仕様なら、こう書きます。

```ts
scenario("投票を作るとDBに保存され、Slackに通知される", async ({ http, db, stub }) => {
  stub("slack").on("POST", "/hook").reply(200, "ok");

  const res = await http.post("/polls", { title: "犬か猫か", a: "犬", b: "猫" });

  expect(res).toHaveStatus(201);
  await expect(db).toHaveRow("polls", { title: "犬か猫か" });
  expect(stub("slack")).toHaveReceived("POST", "/hook", {
    json: { text: "新しい投票: 犬か猫か（犬 vs 猫）" },
  });
});
```

アプリへのリクエスト、DBに書かれた行、Slackに飛んだリクエストを、1つのシナリオの中で確認しています。DBのモックはなく、アプリのコードにテスト用の仕掛けも入れていません。

`.reply(200, "ok")` を `.reply(500)` や `.networkError()` に変えれば、「Slackへの通知に失敗したら、投票の保存もロールバックされるか」も確かめられます。モックのユニットテストでは確かめにくく、E2Eでは再現しにくいところです。

## できること

- アプリの言語は問いません。起動コマンドを渡すだけで、アプリ側はポート・DBのURL・外部APIのURLを環境変数から読めば動きます。リポジトリには Node と Python で同じAPIを実装したサンプルがあり、同じシナリオを両方に流しています
- DBはシナリオごとに TRUNCATE で初期状態に戻すので、テスト同士が干渉しません
- シナリオが落ちると、そのシナリオ中にアプリへ送ったリクエスト、アプリのログ、どのスタブにも一致しなかった外部APIへの呼び出しをまとめて表示します
- TypeScript を書きたくないチーム向けに、同じことを YAML でも書けます

Vitest のプラグインとして動き、Docker か Podman があれば `npm i -D slicetest vitest` で入ります。

## 向いていないこと

- DB は今のところ Postgres だけです
- HTTP で叩けるアプリが対象なので、画面の確認は E2E の仕事です
- 計算やバリデーションのような純粋なロジックは、ユニットテストのほうが速くて的確です
- まだ初期段階のツールです

ユニットテストかE2Eか、どちらかに寄せる話になりがちですが、両方の不満が集まっているのはその間の層だと思っています。そこを埋める道具として作ったので、同じところで困っている人の選択肢になれば幸いです。
