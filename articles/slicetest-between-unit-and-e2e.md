X で「ユニットテストはもう不要、E2Eテストに寄せればいい」という投稿を見かけました。

自分の感覚は少し違います。

E2Eテストは遅いし、メンテナンスにもコストがかかります。AIのおかげで書くのはだいぶ楽になりましたが、ユニットテストで網羅したいような細かいケースまでE2Eで見るのは現実的ではありません。

ユニットテストにも悩みはあります。AIに書かせると、AIが書いた実装をAIが書いたテストで確かめるだけの、自作自演のようなテストになりがちです。それでも、細かいケースまで手軽に確認できるので、品質を担保するにはやはり必要だと思っています。

どちらにも苦手なところがある。だったら、その中間のテストはないのか？ と考えました。

中間に置きたいのはこういうテストです。アプリは本物のプロセスとして動かし、DBも本物を使う。ただしブラウザは使わずHTTPで直接叩き、自分たちの管理外である外部APIだけを差し替える。ユニットテストのようにモックでSQLや外部APIとのやりとりを隠さず、E2Eほど重くしない。

それを書くためのフレームワークとして slicetest を作りました。

- GitHub: https://github.com/revo1290/slicetest
- npm: https://www.npmjs.com/package/slicetest

## ユニット・E2Eとの違い

| | ユニットテスト | slicetest | E2Eテスト |
|---|---|---|---|
| アプリ | 関数・クラス単位 | 本物のプロセス | デプロイされた環境 |
| DB | モック | 本物の Postgres / MySQL | 本物 |
| 外部API | モック | スタブサーバー | 本物かサンドボックス |
| ブラウザ | なし | なし（HTTPで叩く） | あり |

アプリを切り出して（slice）テストするので、この名前にしています。

## どんなテストになるか

「投票を作ると、DBに保存されて、Slackに通知される」という仕様なら、こう書きます。

```ts
scenario("投票を作るとDBに保存され、Slackに通知される", async ({ http, db, stub }) => {
  stub("slack").on("POST", "/hook").reply(200, "ok");

  const res = await http.post("/polls", { title: "犬か猫か", a: "犬", b: "猫" });

  expect(res).toHaveStatus(201);
  await expect(db).toHaveRow("polls", { title: "犬か猫か" });
  expect(stub("slack")).toHaveReceived("POST", "/hook", {
    json: { text: "新しい投票: 犬か猫か（犬 vs 猫）" },
  });
});
```

アプリへのリクエスト、DBに書かれた行、Slackに飛んだリクエストを、1つのシナリオの中で確認しています。DBのモックはなく、アプリのコードにテスト用の仕掛けも入れていません。

`.reply(200, "ok")` を `.reply(500)` や `.networkError()` に変えれば、「Slackへの通知に失敗したら、投票の保存もロールバックされるか」も確かめられます。モックのユニットテストでは確かめにくく、E2Eでは再現しにくいところです。

## できること

0.3.0 時点での内容です。

- アプリの言語は問いません。起動コマンドを渡すだけで、アプリ側はポート・DBのURL・外部APIのURLを環境変数から読めば動きます。リポジトリには Node と Python で同じAPIを実装したサンプルがあり、同じシナリオを両方に流しています
- DB は Postgres と MySQL 8 に対応しています。同じシナリオがどちらでも動き、取得した行の型もそろえています
- DBはシナリオごとに TRUNCATE で初期状態に戻すので、テスト同士が干渉しません。Redis や MinIO のような DB 以外の依存もコンテナとして一緒に起動でき、シナリオごとに `FLUSHALL` などのリセットコマンドを流せます
- シナリオが落ちると、そのシナリオ中にアプリへ送ったリクエスト、アプリのログ、DBに書かれた行の差分、どのスタブにも一致しなかった外部APIへの呼び出しをまとめて表示します
- TypeScript を書きたくないチーム向けに、同じことを YAML でも書けます

Vitest のプラグインとして動き、Docker か Podman があれば `npm i -D slicetest vitest` で入ります。MySQL を使う場合は `mysql2` と、コンテナで起動するなら `@testcontainers/mysql` も入れます。

## 始め方

```sh
npx slicetest init   # スタックを見て設定ファイルと最初のシナリオを書く
npx slicetest        # DBを起動してマイグレーションし、アプリを起動してシナリオを流す
```

`init` は Node、Django、FastAPI、Flask、Rails、Go、Rust のアプリと、Atlas、Prisma、Alembic などのマイグレーションを見分けます。`compose.yaml` があれば、DB のイメージや Redis などの依存もそこから拾います。推測した箇所は設定ファイルにコメントで残るので、そこだけ確認すれば動かせます。

## 外部APIのスタブを本物に近づける

スタブは自分で返り値を書くので、本物のAPIが返すはずのないレスポンスを書いてしまうことがあります。そこを埋めるための機能を足しました。

- 相手の OpenAPI 仕様を渡すと、アプリが送ったリクエストとスタブが返したレスポンスの両方を仕様と照合し、ずれていればシナリオを落とします。`autoReply: true` にすると、ルートを書いていない呼び出しには仕様の例やスキーマから作った値で答えます
- 本物のAPIに一度だけつないで、やりとりを記録できます。`SLICETEST_RECORD=github` を付けて流すと `recordings/github.yaml` に書き出され、以降はネットワークなしで再生します。リクエストヘッダーは保存しないので、トークンがファイルに残りません

## 自分のAPIの抜けを見つける

自分のアプリの OpenAPI 仕様を設定すると、アプリのレスポンスも仕様と照合し、実行の最後に「仕様に書かれたレスポンスのうち、どれをシナリオで出せたか」を表で出します。`npx slicetest gen --uncovered` を実行すると、まだ出せていないレスポンスの分だけシナリオのひな形を YAML で書き出します。

シナリオ1本がやったことをまとめてスナップショットに残すこともできます。

```ts
expect(await trace()).toMatchSnapshot();
```

アプリへのリクエストとレスポンス、スタブへの呼び出し、DBの変更が1つのファイルに入り、日付や UUID は伏せ字になります。挙動が変わるとスナップショットの差分としてレビューに出てきます。

## 向いていないこと

- HTTP で叩けるアプリが対象なので、画面の確認は E2E の仕事です
- 計算やバリデーションのような純粋なロジックは、ユニットテストのほうが速くて的確です
- まだ初期段階のツールです

ユニットテストを捨ててE2Eに寄せるか、という二択ではなく、その間にもう1段置けないか。slicetest はそこから作り始めたものです。
